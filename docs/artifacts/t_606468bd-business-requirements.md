## 6. Пользовательские сценарии

### JS-01 / UC-01 — ручное ведение

**Job Story:** когда я работаю с личным списком на Mini или MacBook, хочу открыть «Личные задачи» в Hermes и вести их в знакомом готовом UI, чтобы не пользоваться вторым самостоятельным списком статусов.

- Участник: владелец. Предусловия: защищённый доступ настроен, собственная служба доступна.
- Основной путь: переход из Hermes → готовый UI Vikunja → создание помеченной тестовой задачи → просмотр → изменение → завершение. Ссылка на задачу открывается на обоих устройствах; чат видит то же изменение.
- Альтернативы: нет доступа — понятный отказ; служба недоступна — сообщение о недоступности без ложного сохранения; после рестарта — та же задача с тем же ID.
- Покрытие: BR-01/02/06/11/12.

### JS-02 / UC-02 — управление из внешнего чата

**Job Story:** когда формулирую личное поручение во внешнем чате, включая Codex, хочу создать или найти задачу, затем изменить/завершить её и получить действительную ссылку, чтобы не переключаться на процесс разработки.

- Предусловия: выбранный адаптер подключён к тому же экземпляру; проверка использует только синтетическое содержание.
- Основной путь: команда создания → подтверждённая запись → ID и ссылка → поиск → выбор найденной задачи → изменение → завершение → сверка в UI. Если поиск неоднозначен, цель должна быть определена до изменения: произвольную задачу не выбирать.
- Альтернативы: срок неизвестен — пусто; относительная дата — `Europe/Moscow`; отказ доступа — нет записи; повтор команды — исходная задача; таймаут после записи — сверка и возврат фактического результата, а не слепой повтор.
- Покрытие: BR-03/06–11/16. Поиск и подтверждение результата не требуют запуска нового coding-agent/dev-flow.

### JS-03 / UC-03 — задача из принятого предложения встречи

**Job Story:** когда предложение по встрече стало моим решением, хочу явно принять его и получить связанную личную задачу, чтобы сохранить происхождение и не превращать все найденные предложения в обязательства.

- Предусловия: существующая синтетическая встреча и предложение доступны; реальная информация встреч не используется в тесте.
- Основной путь: просмотр предложения → явное принятие владельцем → передача названия, даты/времени встречи, краткого контекста, ссылки и подтверждённого срока → создание в Vikunja → возврат ID/ссылки в исходный контекст → открытие задачи и переход обратно к предложению.
- Альтернативы: просмотр/непринятие — нет задачи; нет подтверждённого срока — пустое поле; неоднозначный срок не подменяется догадкой. Повтор принятия — существующая связь, без второй задачи. Запись задачи состоялась, возвратная связь не сохранилась — сверка и восстановление исходной связи. Ошибка доступа — принятие не выдаётся за успешную доставку в трекер.
- Факт принятия предложения и факт успешной передачи различимы. При сбое доставки не нужно повторно принимать предложение или вручную создавать дубль. Техническое поведение этих состояний фиксируется в ТЗ/UX.
- Покрытие: BR-04–06/08–10/13/14.

### JS-04 / UC-04 — продолжение после сбоя

**Job Story:** когда связь оборвалась или Mini перезапустился, хочу узнать фактический результат и продолжить с той же задачей, чтобы не потерять обязательство и не создавать его заново.

- Путь проверки: синтетическая запись → потеря ответа/частичный сбой → сверка в Vikunja → возврат исходного ID → восстановление связи → рестарт → повторное открытие задачи/вложения.
- Если исход не установлен, состояние остаётся неопределённым с понятным действием восстановления; успех не придумывается. Резервная копия и восстановление проверяются безопасно по согласованному плану, без восстановления поверх реальных данных ради теста.
- Покрытие: BR-08/09/12/13/17.

### Минимальные состояния взаимодействия

| Поверхность | Что должно быть различимо пользователю |
| --- | --- |
| «Личные задачи» | Понятное назначение перехода, корректное открытие готового UI; доступ/недоступность не маскируются под пустой список |
| Ответ чата | Подтверждённый успех с ID/ссылкой, нет совпадений/неоднозначный поиск, ошибка доступа, неизвестный исход и необходимость сверки |
| Предложение встречи | Не принято; явно принято, но ещё не подтверждена передача; передача подтверждена со ссылкой; ошибка/неопределённый исход; связь восстановлена. Это смысловые состояния, не утверждённые новые подписи кнопок или редизайн |

Ссылки и действия должны быть понятными и доступными для использования владельцем; конкретные UX-состояния, размещение и критерии доступности уточняет предусмотренный UX-этап без расширения scope «Встреч».

## 9. Неизвестное, допущения и передача следующим этапам

**Блокирующих пробелов уровня бизнес-цели/объёма для подготовки этих БТ не выявлено:** обязательные результаты, запреты и порядок личной приёмки заданы S1. Неизвестные технические факты ниже не подменены решениями и должны быть разрешены в своих документах до зависимых работ. Если выяснится необходимость изменить границы S1, потребуется отдельный самодостаточный вопрос владельцу, а не молчаливое расширение.

| Неизвестное | На что влияет / где требуется разрешить |

| Подходящий MCP/адаптер, поддержка Codex и безопасное подключение | Архитектура и ТЗ; подтвердить фактические возможности всех требуемых действий, не обещать их по названию инструмента |
| Идентичность логической операции, восстановление соответствия «предложение ↔ задача», поведение поиска и доступность ссылок | ТЗ/UX и проверки; должен выполняться результат BR-05/08/09, без предписания схемы БД или API в БТ |
