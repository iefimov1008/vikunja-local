## Проблема

Три канала должны управлять одними личными задачами без независимых статусов, дублей и самовольного принятия предложений. Уже подготовленная среда содержит данные и незавершённые компоненты; её нельзя считать пустой или готовой интеграцией. Основание: БТ §2–3, BR-01–18, ADR «Контекст».

## Цель

Определить проверяемое поведение установки и общего адаптера `vikunja-local`: CRUD через UI/чат, узкая передача принятого предложения, устойчивое соответствие и восстановление. По принятому A1 сформулировать целевые инварианты, а недоказанные wire-контракты оставить условными с точными критериями закрытия. Не реализовывать второй трекер или dev-flow для личных задач.

## Диаграмма последовательности

Ниже — **целевая последовательность требований по ADR/A1**, не отчёт о работающем мосте и не новый транспортный контракт. По R3 текущая цепочка `DecisionDialog → POST .../decision → authorize → Core.decision → локальная Markdown-задача` ещё не подтверждает создание в Vikunja. Hosted owner principal, точная реализация durable event/outbox и защищённого сохранения backlink остаются условиями Q-02 / G-04.

```mermaid
sequenceDiagram
  actor Owner as Владелец
  participant Hermes as Hermes: существующее принятие
  participant Outbox as Долговечное событие и outbox
  participant Adapter as Единый адаптер
  participant Journal as Долговечный журнал операций
  participant Vikunja as API Vikunja
  Owner->>Hermes: Явно подтвердить текущую версию, название и срок/отсутствие
  Hermes->>Hermes: Проверить owner principal, Origin и версию
  alt Нет прав, отмена или устаревшая версия
    Hermes-->>Owner: Отказ / обновить подтверждение, без передачи
  else Авторизованное принятие
    Hermes->>Outbox: Сохранить принятие и восстанавливаемое намерение доставки
    Note over Hermes,Outbox: Разрыв между ними не должен терять доставку; G-04
    Outbox->>Adapter: Доставить тот же стабильный источник/версию/событие
    Adapter->>Journal: Сериализовать операцию и сохранить намерение до HTTP
    alt Журнал недоступен или нет доказанного принятия
      Adapter-->>Outbox: Отказ, без внешней мутации
    else Новая операция, безопасный первый create разрешён
      Adapter->>Vikunja: Create с происхождением и маркером в том же запросе
      Note over Adapter,Vikunja: C1: сбой после отправки/commit до receipt — unknown
      Adapter->>Vikunja: Read-back ID либо полная точная сверка маркера
      alt Одно точное соответствие и объект прочитан
        Adapter->>Journal: Сохранить receipt и соответствие реальному ID
        Note over Journal,Hermes: C2: сбой до backlink — восстанавливать только связь
        Adapter-->>Hermes: Подтверждённый ID и проверенная ссылка
        Hermes->>Hermes: Сохранить backlink с проверкой версии/связи
        Hermes-->>Owner: Передано в Vikunja
      else Ноль после unknown, несколько или чтение недоступно
        Adapter->>Journal: Сохранить unknown / конфликт / отказ чтения
        Adapter-->>Owner: Проверить передачу, без нового create
      end
    else Повтор / восстановление существующей операции
      Adapter->>Vikunja: Сверить прежний ID/маркер без нового create
      Adapter-->>Hermes: Прежний проверенный ID либо unknown/конфликт
    end
  end
```

Сбой C0 до долговечного намерения запрещает HTTP; после рестарта одного наличия намерения недостаточно для вывода «HTTP не отправлен». Операция с возможным внешним вызовом переходит к сверке. Сбои C1/C2 не отменяют принятие. При неизвестном исходе ноль совпадений **не разрешает повторный create**; в этой редакции альтернативная серверная защита повтора не доказана. Прямой UI Vikunja вне адаптера сохраняется, поэтому локальная блокировка не защищает от ручного конкурентного update. Условные части последовательности проверяются G-01–G-05, а не засчитываются по самой диаграмме.

### Даты и адреса

Подтверждённые правила: неизвестный срок пуст; срок встречи не становится дедлайном; предложение требует явного подтверждения срока/отсутствия; изменение срока сбрасывает подтверждение; относительные даты — Europe/Moscow и абсолютное представление пользователю (UX §3–4). Требуется сохранить фиксированный контекст вычисления при повторе, не пересчитывать «завтра» заново после полуночи.

P8 сообщает reference_msk=2026-11-08T23:55:00+03:00, relative_date_msk=2026-11-09, api_roundtrip=2026-11-08T21:00:00Z; explicit_null_http=201, explicit_null_roundtrip=0001-01-01T00:00:00Z. Это наблюдение представления API, не выбор политики date-only или доказательство очистки update; UI не проверен. ❓ Опорное время (команда/подтверждение), date-only, omission/очистка требуют Q-04; произвольная полночь/23:59/UTC не назначаются. Неоднозначный срок ожидает уточнения, без guessed deadline. Дата/время встречи сохраняют свой смысл отдельно от due.

Конкретные UI/API origin, task URL template, SSH host/user/port и MacBook local forwarding endpoint не установлены. `127.0.0.1:9345` из R1 — наблюдённый listener, **не** принятый URL для всех клиентов. Рабочие ссылки требуют A1/P9 и read-back одного ID на двух устройствах; secrets не включаются в URL/argv. Аутентификация приложения сохраняется поверх SSH.
